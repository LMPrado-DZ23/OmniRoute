- **perf(budgets):** the workspace/project budget roll-up asked SQLite once **per key**, on a path that runs for every request carrying a project-scoped key — measured at 129 `prepare()` calls to answer a single 100-key check. The committed half is now one `SELECT … WHERE api_key_id IN (…)` for the whole set, chunked at 400 ids to stay well under SQLite's 999-variable limit; the pending half still walks the in-memory write buffer, which never touches the database. Key ids are **bound, never interpolated** — the placeholder list is built from the array's length — and a test passes a hostile id and asserts it never reaches the SQL text, because these identifiers are user-created. Measured rather than asserted: a test counts the statements and fails at 100 selects if the batching is undone, and another checks the batched total still equals the per-key total it replaced.
